# 设计说明

## 先验证，再总结

流程编码与系统必须匹配。规则请求失败、审批规则为空、字段映射缺项或重复时抛出异常，进入人工处理提示。规则不是可选的背景信息，不能在获取失败后让模型自行补全。

字段配置包含标签、路径、类型和是否必需。先完整查找路径，再解包 `fdName` / `value`；中英文不分开过滤，避免数组错位。只对 `datetime_ms` 类型转换时间，固定 UTC+8。金额不通过大小猜测类型。

## 确定性计算

采购数据用十进制核对单价×数量、明细小计和总额。不一致则停止生成总结，交由人工查看原始材料。模型不承担计算准确性的保证。当前业务契约要求明细金额精确一致；若增加税费、折扣或舍入，需先明确规则并增加样本。

## 附件完整性

规则明确必需附件名称。必需附件缺失或解析失败时停止处理；可选附件失败保留名称与 `failed` 状态，并设置 `incomplete=true`。模型被要求说明材料不完整，只整理事实与待核实项。

演示解析服务接收核对规则，返回固定夹具和已收到的规则。此设计验证数据流，不验证真实解析能力。没有附件、附件解析失败、附件解析成功分别表达。

附件串行处理，每次节点调用内复用一个模拟 token；未实现并发、跨请求缓存或真实凭据刷新。HTTP 和模型节点保留声明式重试，代码节点请求失败直接走失败分支。

## 模型输入与输出

可信规则置于 system 消息，表单和附件放在 user 消息。提示词明确业务内容中的命令不是系统指令，禁止推断历史记录、市场价格和签字真实性。但提示词隔离不提供安全保证，仍需用攻击性样本验证实际模型行为。

模型固定输出关键信息、核对结果、待人工确认。输出节点保留原文中的方括号和 Markdown，避免误删证据，拒绝空输出，并追加人工审批边界。输入 JSON 的作用是保留字段与类型，不声称优于其他格式。

## 模拟写回与展示

BPM 总结先请求模拟回调，再展示总结与写回状态。失败时不抛弃已有文本，也不宣称已同步。Mock 保存最新内容供读取核验；进程重启清空。没有持久化、真实审批动作或流程节点唤醒。

两条业务分支的源代码各自完整嵌入 DSL，便于直接导入。测试从 DSL 读取实际代码，避免只测试另一份未部署实现。修改 YAML 内代码后，应同时跑回归测试与对应的 Dify 验收场景。
