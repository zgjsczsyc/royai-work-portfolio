# 案例导览

作品集围绕三条线展开：将业务约束整理成 AI 工作流、通过数据理解工具使用、把异步任务和信息分析做成可交互的产品。建议先阅读前三个案例，再按兴趣查看补充项目。

## 1. 企业审批辅助：将业务规则落实到工作流

**问题**：审批表单和附件来自不同系统，字段、日期和材料状态不一致。模型如果直接总结不完整的数据，可能给出缺少依据的结论。

**方案与取舍**：Dify 编排 OA/BPM 两条适配路径。先获取规则并校验必需字段、附件和采购金额，再组织模型输入。金额由确定性代码核对；缺少关键资料时转人工。模拟写回后再向使用者显示实际写回状态。

**展示产物**：工作流 DSL、示例规则、本地 Mock、设计说明和异常回归测试。用户已确认内置数据版在 Dify Cloud 可运行；接口集成版由本地 Mock 验证。逐场景云端运行记录和模型质量评测仍需补齐。

[案例说明](../projects/approval-assistant/docs/case-study.md) · [工作流与启动方法](../projects/approval-assistant/README.md) · [验证边界](../projects/approval-assistant/docs/validation.md)

## 2. AI 平台运营：从指标观察到进一步研究

**问题**：总访问量无法说明谁在使用工具、哪些渠道和部门在持续使用，也无法直接解释采纳障碍。

**方案与取舍**：按时间、Web/数字员工渠道、部门和用户分层查看访问与活跃。切换筛选后同步重算指标，以同一份合成样本展示统计口径。界面观察用于提出问题，不直接推断因果或投资回报。

**展示产物**：运营看板、聚合代码、90 天合成样本及实际运行截图。原平台数据不在仓库中；当前证据支持对统计逻辑与使用结构的讨论，不支持真实增长归因。

**两分钟演示**：先看整体趋势，再切换渠道与近 30 天，选择一个部门或用户层级，说明下一步还需要哪些访谈或数据来判断原因。

## 3. FC Social Radar：从讨论材料到可追溯判断

**问题**：跨平台互动量不可直接相加；讨论热度高也不等于与目标产品高度相关。运营判断需要能回查证据，并保留不确定性。

**方案与取舍**：分开计算样本热度、产品关联和潜在影响。对具体事件聚合并保留引用、原文、评分解释和待核实项。真实采集与合成展示隔离，公开入口为只读快照。

**展示产物**：三平台采集适配、事件看板、中文简报、真实公开来源快照和验证记录。人工质量验收与跨日稳定性仍待完成；游戏场景中的方法可用于讨论其他行业的信息观察需求，不代表已在品牌、医药或 ESG 场景落地。

[完整案例](../projects/fc-social-listening/docs/portfolio-case-study.md) · [在线快照](https://zgjsczsyc.github.io/fc-social-radar-snapshot/) · [验证记录](../projects/fc-social-listening/VALIDATION.md)

## 能力与证据对应

| 能力方向 | 本仓库可查看的证据 | 证据范围 |
| --- | --- | --- |
| 业务拆解与方案设计 | 审批规则、失败路径、通知两类未读状态、舆情评分取舍 | 设计和实现可查看；历史协作分工不由代码证明 |
| AI 工作流搭建 | Dify DSL、系统适配、输入校验与本地回归 | 用户已确认云端演示可运行；逐场景记录、模型质量及 Dify 中的业务接口联调待验证 |
| 数据整理与分析 | 字段映射、日志分类、运营聚合、样本内热度与证据回查 | 以合成数据或注明范围的公开样本验证 |
| 产品交付与用户体验 | 多个可运行界面、运行说明、截图与自动化验证 | 展示功能节选，不等于完整企业系统 |
| 工具推广和效果评估 | 运营指标视角、演示路径与验证方法 | 尚未收录培训、工作坊、用户采纳实验或真实 ROI 证据 |
